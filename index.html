SQL Server tuning case study

A fictional multifinance database with about 4.8 million installments and three slow queries that show up in almost every financing system. Each one comes with the diagnosis, the fix, what the fix costs, and a rollback.

  1. Scenario 1

    Contract lookup by number

    Problem
    No index on ContractNo, and the app sends an NVARCHAR parameter to a VARCHAR column.
    Fix
    Unique index plus the correct parameter type. The index alone still scans because of CONVERT_IMPLICIT.
    Cost
    One narrow index, plus finding every caller that sends the wrong type.

  2. Scenario 2

    Delinquency report by DPD bucket

    Problem
    DATEDIFF and ISNULL on columns make the filter non-sargable, so every installment is read.
    Fix
    Sargable rewrite and a filtered index that holds only unpaid installments.
    Cost
    Each payment posting touches the index. Equivalence holds only without partial payments.

  3. Scenario 3

    Monthly collection per branch

    Problem
    Three correlated subqueries re-read the installment table, filtered with YEAR() and MONTH().
    Fix
    One pass over a half-open date range with a covering index on DueDate.
    Cost
    A wide index on the largest table. Its size is measured before deciding to keep it.

How I tune a query

  1. Capture a baseline: logical reads, CPU, duration.
  2. Read the actual plan for scans, warnings, and bad estimates.
  3. Change one thing, then measure again.
  4. Prove the result set is identical.
  5. Count the write and storage cost.
  6. Ship it with a rollback script.
